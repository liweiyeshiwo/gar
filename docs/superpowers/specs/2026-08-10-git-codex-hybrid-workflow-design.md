# 本地 Codex × GitHub × Codex cloud 混合开发工作流设计

状态：方案 A 已选定；详细规格待用户复核

日期：2026-08-10

适用仓库：`liweiyeshiwo/gar`

## 1. 背景与设计目标

`gar` 当前是一个没有提交、代码或既有约定的空 GitHub 仓库。本设计先把它建设为可复用的软件开发工作流基座，而不预设未来应用的语言或框架。

工作流需要同时支持：

- 本地用户与本地 Codex 进行需求澄清、架构判断、交互式开发和本机调试；
- 把边界明确、可由仓库独立复现的任务交给网页版 Codex cloud；
- 通过 GitHub 分支、提交、Pull Request（PR）和检查传递上下文与证据；
- 由本地完成最终复验，并由用户保留合并与发布决定权；
- 将重复出现且已经验证的经验沉淀到测试、CI、`AGENTS.md` 或工作流文档。

成功标准是：任何一次本地—云端交接都能从一个明确 commit SHA 复现；云端产出可通过 PR 审查；合并前有本地与 CI 的验证证据；主分支不接受代理直接写入。

## 2. 非目标

本阶段不做以下事项：

- 不选择应用技术栈，不创建虚构的 `src/` 或业务代码；
- 不让 Codex cloud 直接向 `main` 写入或决定合并；
- 不把普通 ChatGPT 网页对话当作代码交接介质；
- 不用 Codex review 替代测试、CI、分支保护或人工判断；
- 不把本地未提交状态、密钥或机器专属配置同步到 Git；
- 不在 CI 首次成功运行前配置一个尚不存在的 required check。

## 3. 核心架构

GitHub 是唯一共享状态，draft PR 是默认任务界面，commit SHA 是交接原子。

工作流由五个边界清晰的组件组成：

1. **本地工作区**：保存正在探索的状态，负责需求、设计、本机调试和最终复验。
2. **仓库契约**：由 `AGENTS.md`、工作流文档、任务模板和验证命令组成，向本地与云端提供同一套规则。
3. **Git 交接层**：用短分支、原子提交和不可歧义的 commit SHA 固化可交接状态。
4. **Codex cloud 执行环境**：从指定分支或 SHA 检出代码，执行独立任务，运行仓库声明的检查并回传 diff。
5. **GitHub 门禁**：用 PR、Actions、对话解决和 Codex review 暴露变更与风险，合并权保留给用户。

仓库目标结构：

```text
AGENTS.md
README.md
docs/
  development-workflow.md
  research/
  superpowers/specs/
.github/
  pull_request_template.md
  workflows/ci.yml
```

由于当前仓库只承载工作流基座，首版 CI 仅验证仓库结构、文本基本质量与工作流文件有效性。未来加入真实应用后，再由该应用的技术栈定义安装、lint、typecheck、test 和 build 命令。

## 4. 职责分工与任务路由

### 4.1 本地优先任务

以下工作默认留在本地：

- 需求尚不稳定、需要与用户频繁确认的探索；
- 架构取舍、模块边界与高影响设计决策；
- 依赖本机 GUI、硬件、私有数据库、局域网服务或未提交状态的调试；
- 小而交互频繁、云端启动成本高于执行成本的修改；
- 云端结果的 diff 审查、完整复验、合并和发布判断。

### 4.2 云端优先任务

同时满足以下条件的任务优先交给 Codex cloud：

- 输入已经提交并推送；
- 目标、非目标和允许修改的范围明确；
- 验收标准可观察，验证命令可在隔离环境运行；
- 不依赖本机隐含状态；
- 适合后台运行、批量处理或独立审查。

典型任务包括：独立功能实现、补测试、修复 CI、依赖升级、机械迁移、跨目录一致性修改、文档同步和 PR 代码审查。

### 4.3 禁止云端执行的任务

不得把以下任务交给云端代理：

- 需要生产密钥在代理执行阶段持续可见的操作；
- 直接操作生产数据、发布生产版本或合并 `main`；
- 无法由仓库和云环境重建的机器专属操作；
- 没有验收标准且可能产生大范围自主重构的开放式请求。

## 5. 标准状态流

每项工作按以下状态推进：

```text
意图形成
  -> 本地任务契约
  -> 功能分支
  -> 本地实现或交接提交
  -> push + draft PR
  -> 云端执行
  -> PR diff + Actions + Codex review
  -> 本地复验
  -> 用户合并
  -> main 同步与沉淀
```

状态转换规则：

- 没有提交并推送，不得从“本地实现”进入“云端执行”；
- 没有固定 commit SHA，不得宣称交接完成；
- Actions 失败或本地复验失败，不得进入“用户合并”；
- 只有用户可以把 PR 从“可合并”转换为“已合并”；
- 未经验证的一次性经验只保留在 PR，不进入长期规则。

## 6. 分支、提交与所有权

- 每项无关工作使用独立短分支，默认命名为 `codex/<task-slug>`；
- 交接提交必须保持可构建或明确记录已知失败，提交消息建议为 `chore: checkpoint for cloud handoff`；
- 同一功能分支在同一时间只有一个主动写入者：用户、本地 Codex 或云端 Codex；
- 交接时先提交、推送并记录 SHA，再声明写入权转移；
- 云端执行期间，本地不得改写该分支历史或 force push；
- 若必须并行，使用互不重叠的分支，并通过单独的集成 PR 汇合；
- 代理不得直接写入 `main`，不得删除分支或仓库内容。

## 7. 交接契约

每次云端任务必须在 draft PR 描述或任务提示中包含：

```text
Base: <branch> @ <commit SHA>
Goal: <可观察结果>
Non-goals: <明确排除项>
Allowed scope: <允许修改的目录或文件>
Constraints: Follow AGENTS.md; do not write to main
Verify: <精确命令>
Deliver: Push only to this feature branch; summarize files, tests, and risks
```

PR 需要持续记录：

- 任务目标与范围；
- 本地交接 SHA 和云端最终 SHA；
- 已执行的验证及结果；
- 尚未覆盖的风险；
- 截图、迁移说明或回滚方法（如适用）。

普通网页版 ChatGPT 可以用于研究、讨论或起草，但代码接力必须落到具备 GitHub 仓库和云环境能力的 Codex cloud。

## 8. `AGENTS.md` 与云环境契约

根 `AGENTS.md` 只记录耐久、可执行的规则：

- 项目目的与关键目录；
- 唯一安装与验证入口；
- 完成定义；
- 敏感信息和生产操作边界；
- PR 必须携带的验证证据；
- 少量需要语义判断的 `## Code Review Rules`。

机械规则应尽量进入 formatter、linter、测试或 CI，不应堆入语义审查提示。

Codex cloud 环境需要固定关键运行时和包管理器版本。setup script 只负责可复现安装；代理阶段默认不联网，确需联网时使用最小范围授权并在 PR 记录原因。secret 不写入仓库，也不假定其在代理阶段仍然存在。

## 9. GitHub 门禁

个人仓库的起步门禁为：

- 所有变更通过 PR；
- CI 的唯一稳定检查成功；
- PR 对话全部解决；
- 禁止强推或删除 `main`；
- 重要 PR 执行 Codex review；
- 合并前本地复验；
- 最终合并由用户执行。

首版 Actions 成功运行后，才把实际出现的 job 名设为 required status check。个人仓库不强制不存在的第二名人工批准；未来有真实合作者后，再增加独立审批和 CODEOWNERS。

## 10. 失败处理与恢复

### 云端无法安装或验证

云端停止扩展修改范围，在 PR 中报告失败命令、日志摘要和环境差异。本地判断是补充仓库脚本、修正云环境，还是把任务收回本地。环境修复必须独立验证后再重新交接。

### 云端修改超出范围

不直接合并。以交接 SHA 为基线审查 diff，要求云端在同一分支追加纠正提交，或从基线创建新分支重新执行。禁止通过改写共享历史掩盖问题。

### 本地与云端发生冲突

立即停止其中一个写入者。保留双方提交，在新的集成分支上显式解决冲突并重新运行全部检查，不 force push 覆盖任一方成果。

### CI 与本地结果不一致

以可复现性问题处理：比较运行时、锁文件、环境变量、操作系统和命令入口。修复应优先沉淀到锁文件、脚本或 CI，而不是只记录为口头例外。

### 云端结果无法达到验收标准

任务返回本地重新拆分。保留失败 PR 作为证据，不把未经验证的规则写入 `AGENTS.md`。

## 11. 验证策略

验证分为四层：

1. **提交前检查**：工作树、staged diff、敏感信息和 `git diff --check`；
2. **云端自证**：执行交接契约中的精确命令并汇报结果；
3. **GitHub 门禁**：Actions 和 Codex review；
4. **本地最终复验**：拉取云端最终提交，重新运行完整检查并审查任务范围。

只有四层均满足时，工作流才把任务标记为可合并。

## 12. 最小验收演练

完成工作流骨架后，用一个无风险任务验证端到端链路：

1. 本地创建 `codex/handoff-smoke-test`；
2. 提交一个明确、可验证但尚未完成的文档或测试任务；
3. 推送并创建 draft PR，记录交接 SHA；
4. 从 Codex cloud 基于该 SHA 完成任务；
5. 检查云端 diff、Actions 和 Codex review；
6. 本地拉取最终提交并运行完整验证；
7. 用户确认后合并并同步 `main`；
8. 将演练中唯一真实、可复用的问题沉淀到测试、CI、环境脚本或 `AGENTS.md`。

验收演练通过后，才认为混合工作流已经可用，而不只是文档化。

## 13. 分阶段落地

### 阶段 1：仓库基线

建立 README、根 `AGENTS.md`、正式工作流文档、PR 模板和最小 CI，创建并推送首个 `main` 提交。

### 阶段 2：云端连接

在 Codex cloud 授权该仓库，建立最小权限云环境，确认能读取 `AGENTS.md` 并运行仓库验证入口。

### 阶段 3：交接演练

按第 12 节执行一次 draft PR 接力，记录实际结果并修正规则。

### 阶段 4：门禁加固

CI 成功出现后配置分支保护与 required check；有真实合作者后再增加独立人工审批和 CODEOWNERS。

## 14. 设计决策摘要

- 采用本地主导、云端选择性接力，而不是云端全面自治；
- 用 GitHub 版本化状态替代聊天记录或隐含本地状态；
- 用 draft PR 统一任务、讨论、检查和交付；
- 用 commit SHA 明确交接基线；
- 用单写入者规则避免本地与云端互相覆盖；
- 用 CI 和本地复验构成硬门禁，用 Codex review 提供语义审查；
- 用户始终保留合并、发布和生产操作权限。
